# IRIS — Product Specification

## 1. Product definition

Iris is an executive-function operating system for students.

Iris reduces the executive-function effort required to turn messy thoughts, responsibilities, deadlines, events, and intentions into useful actions. It is not a generic todo list.

The AI transforms messy human input into a useful starting point. The user decides what is actually true.

AI suggestions are editable. Human edits are authoritative. Nothing generated by AI is immutable.

## 2. Product philosophy

- Iris should help the user begin.
- AI should offer useful structure, not claim objective certainty.
- The user should be able to change the result at every meaningful point.
- Iris should adapt to user corrections instead of forcing the user to adapt to the AI.
- Iris should be calm, forgiving, spacious, human, intelligent, intentional, and slightly playful.

Iris must avoid guilt-driven productivity design, overwhelming checklists, dense dashboards, unnecessary complexity, and generic corporate SaaS aesthetics.

## 3. AI and human responsibilities

### AI

- Proposes an interpretation and plan from the user's input.
- Separates information semantically and preserves relationships where possible.
- Asks useful clarification questions when information is ambiguous.
- Produces actionable, recoverable plans.
- Does not silently overwrite human corrections.
- Does not reinterpret the user's reality after every small manual edit.

### Human

- Reviews the AI's interpretation.
- Corrects what is inaccurate or incomplete.
- Decides the current reality, priorities, and placement of work.
- Can override AI placement through editing and drag-and-drop.

The corrected human reality is the source of truth. Replanning may occur when appropriate, but manual edits remain authoritative.

## 4. Product workflow

The intended end-to-end workflow is:

1. Brain dump
2. Interpretation
3. Clarification
4. Human correction
5. Planning
6. Date-based dashboard
7. Universal editing
8. Universal drag/drop
9. Confirmation before relocation
10. Persistence
11. Adaptive replanning
12. Eventually reminders/timer

This sequence defines Iris's product direction. It is not permission to implement all stages at once.

## 5. Current product requirements

The current product must support the following workflow requirements.

### 5.1 Brain dump

The user can write naturally and messily. They do not need to classify information in advance as a task, deadline, event, reminder, routine, note, idea, or non-negotiable.

### 5.2 Interpretation and clarification

Iris should infer structure from a brain dump and classify information semantically rather than treating every line as an independent task. It should preserve relationships between information where possible.

Iris must not invent dates, times, deadlines, commitments, chapters, syllabus details, priorities, durations, or requirements.

When information is ambiguous, Iris should ask useful clarification questions. The user can manually correct the resulting interpretation.

### 5.3 Planning

Planning begins from the human-corrected interpretation. The plan is a starting point, not a fixed prescription.

Plans should:

- turn vague work into genuinely actionable steps;
- work backward from deadlines and events when useful;
- remain generic when the user supplied insufficient information;
- be forgiving and recoverable;
- avoid filling every available minute with work.

For a generic test, steps such as reviewing available material, marking unclear areas, practicing representative problems, reviewing mistakes, and creating a final-review list are appropriately actionable. A task such as “Study physics” is not sufficiently actionable on its own.

### 5.4 Dates and time

Actual normalized dates are stored internally when relative language can appropriately be resolved using the user's local date and time.

Examples include today, tomorrow, in 2 days, and next Friday. Actual calendar dates must be visible in the interface. Relative wording may be retained when useful, but normalized dates are the source of truth for scheduling.

### 5.5 Date-based dashboard

The dashboard prioritizes:

- what matters today;
- what can actually be done next;
- upcoming anchors;
- protected time;
- future planned work.

Today is visually primary. The dashboard should not become a dense project-management interface.

### 5.6 Manual placement and relocation

Manual placement overrides AI placement. Tasks should be movable wherever they logically belong, including:

- one interpretation category to another;
- today to tomorrow;
- tomorrow to today;
- one future day to another;
- reordering within a day.

Meaningful drag-and-drop relocation requires a calm confirmation step before the change is committed. The confirmation explains what is moving, where it is currently located, and where it will go. Cancel leaves state unchanged; confirm commits the user's decision.

## 6. Universal editability

Universal editability is a required product direction, but its complete implementation is not required all at once.

The user should eventually be able to edit essentially anything that represents their reality, including tasks, subtasks, deadlines, events, reminders, routines, notes, ideas, protected time, planned task descriptions, plan focus, dates, and times.

Editing should be direct and lightweight. The preferred interaction is:

`hover → editable cursor or affordance → click → inline editing`

The user should not need to invoke AI merely to change text.

## 7. Persistence and adaptive behavior

Persistence is a future requirement, not an instruction to implement it in the current milestone. Iris should eventually preserve user state across refreshes, reopening the app, and restarting the development server. The initial persistence solution should be simple and reliable. Cloud synchronization is a future goal.

Adaptive replanning is also future direction. It must preserve manual edits as authoritative rather than silently replacing them.

## 8. Longer-term direction

Iris should eventually become an adaptive executive-function assistant rather than simply a planner.

Potential future capabilities are:

- adaptive replanning;
- reminders;
- timers;
- context-aware task suggestions;
- energy/time-aware planning;
- cross-device synchronization;
- integrations with the user's existing tools.

These are directional goals, not current MVP commitments.

## 9. Technical constraints

The current stack is React, Vite, Node, Express, JavaScript, OpenRouter, and Git/GitHub. Development should remain compatible with this stack unless there is a compelling reason to change it.

Iris should prioritize low-cost development, with a target total spend of approximately ₹500 maximum. Existing available tools and services should be preferred where appropriate.

API secrets must remain server-side.

## 10. Scope boundary

This specification defines what Iris is. Implementation must proceed in coherent milestones rather than attempting to build the entire long-term direction at once.
